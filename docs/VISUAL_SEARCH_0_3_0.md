# Подготовка снимков — 0.3.0

Продолжение работающего stage2 и компактного UI0.2.5. Новое поручение владельца
03.11.2026 разрешает разработку/внедрение улучшателя; прежнее ограничение
«только анализ» снято. До правок clean main5f82ff5 синхронизирована fetch/ff-only.

## Поток и границы

Смартфон → прежний HTTPS8443 Linux gateway → прежний TLS/HMAC Windows9443.
Новых публичных портов/ключей/облачных API нет. Нативный compute остаётся
изолированным дочерним процессом рядом с ОперКонтуром. Индекс/schema/DINO
не заменяются; фоновые задания, namespaces, составы комплектов и источники
сохраняются. Разделы управления ОперКонтура остаются admin-only.

Алгоритм: исходный поиск; при отсутствии confirmed и свободном admission —
подготовка и до двух дополнительных поисков в том же индексе. Сначала
попытка выделить известный печатный рисунок по согласованным SIFT/RANSAC
признакам первых кандидатов. Затем уверенная плоская граница OpenCV; иначе
U2NetP предлагает маску основного объекта. Маска не считается распознаванием
артикула: малые/неоднозначные/крайние объекты отбрасываются, отверстия силуэта
заполняются, край расширяется. Неуверенность оставляет полный исходник.

После выделения — поиск без дорисовки. При score>=.92 и исходных деталях
crop inliers>=12/support>=.30 обработка может закончиться на этой стадии.
Иначе DHAN-SHR256CPU даёт низкочастотную поправку в ярких малохроматических
областях. Поправка ограничена; сетевые высокочастотные детали не подменяют
исходник. Слабый bilateral при выраженных высоких частотах, gain<=1.2 для
тёмного кадра. Это эвристики, а не универсальная физическая реконструкция.

Производные ветви объединяются по коду с штрафом.045, без сложения оценок.
Confirmed исходника защищены; первый исходный кандидат с inliers>=12 и
support>=.30 сохраняет позицию без нового зелёного статуса. Производная
ветвь сама по себе всегда uncertain/weak. Текущая score не вероятность.
Namespace и заранее выбранный вид не расширяются. При смене поколения
между двумя стадиями используется исходная выдача, не смесь индексов.

## Интерфейс и отказ

В существующем окне кадра добавлены Авто/Улучшить/Исходник/Обработка.
Результаты, фильтр RAM, четыре нижние кнопки, квадрат камеры и маркировка
сохранены. Авто задаёт fallback при слабом результате; выключение отправляет
enhancement=off. Просмотр обработки не меняет исходные пиксели. Найти при
показанной обработке отправляет исходник с force: сервер повторяет обработку
и ищет исходник вместе с вариантами. Это дополнительное вычисление после
предпросмотра; server image cache намеренно отсутствует. Переключение на
исходник с выключенным Авто позволяет искать только исходный кадр.

Фотографии — только RAM во время запроса/открытого кадра. Сервер сохраняет
только metadata результата TTL90s; кадры/preview не пишутся в задания,
каталог, историю, storage или логи. Следующий/новый файл/close освобождают
клиентские canvas; operation counter исключает поздний ответ. Передача
только явными Улучшить/Найти. OS paging/WER остаётся границей гарантии.

Тот же session/origin/content-type/2MiB/12Mpx/TLS/HMAC/subject admission для
POST enhance. Тяжёлая дополнительная работа не стартует впереди другого
сотрудника. Ошибка/таймаут optional стадии возвращает сохранённую исходную
выдачу; отдельный preview сохраняет исходный кадр для повтора. Parent
восстанавливает только свой compute при hard timeout. Метаданные/frames
старого запроса не применяются к новому кадру.

Лимиты: queue5, один compute, torch2/OpenCV1, CPU группы10%; память группы
планируется4GiB, compute3GiB по разрешению владельца (физически32GiB RAM).
На момент замера свободно14–15GiB. Дополнительная compute стадия <=12s,
обычный admission/execution<=18s; gateway22s, browserPOST23s. Штатные429/503
возможны при перегрузке. Лимит CPU по коротким окнам не объявляется строгим
из-за ранее измеренных особенностей Windows job accounting.

## Проверки и ограничения

Проверки фиксируются отдельными измерениями после установки. Unit-тесты
проверяют права, signed paths, отказ, busy/off, сохранение исходника и
невозможность нового green по производному изображению. Browser synthetic
проверяет актуальные assets, preview/retry/compare/отмену, точный исходный
JPEG при поиске обоих, существующие фильтры/сетку/штрихкод и размеры экранов.
Это не приёмка физических смартфонов.

Полностью белый блик не содержит рисунка. Один снимок не показывает обратную
сторону кружки; общая гомография не разворачивает цилиндр/мятый пакет.
Saliency может выделить часть рисунка, SIFT — похожий шаблон; исходная ветвь
и консервативное объединение обязательны. Генеративное обучение/дорисовка
артикулов не выполняются. Владелец собирает реальные фото: их нужно разметить
кодами и разделить по товарам на настройку/независимую проверку перед заявлением
о качестве на настоящих бликах. Учебная и контрольная выборки не смешиваются.

Откат — восстановить сохранённый installation/config Windows и прежний
gateway container/source, адресно перезапустить только вычислитель/шлюз.
Старый индекс/current, БД, файлы, сертификаты и задачи автозапуска не менять.
Legacy app CMD включает migrate.py: контейнер приложения/БД не перезапускать;
при SSE reload завершать только проверенный старый HTTP child, родитель жив.

## 0.3.1 — реальные товары, фрагменты и воспроизводимое пополнение

Алгоритм enhancer-1.1. Полные макеты в каталоге могут содержать обе стороны,
несколько значков или развёртку кружки. Новая схема physical-layouts-2 сохранена
в services/visual_search/product_profiles.py. Это общие правила по виду товара,
без кодов конкретных товаров и без фотографий из контрольной выборки.

| Вид | Дополнительные представления исходного макета |
| --- | --- |
| Обложки паспорт/военник/студенческий, дневники | Левая и правая половины с перекрытием, правая область 72% |
| Пеналы | Левая/правая и верхняя/нижняя половины с перекрытием |
| Минидаки | Те же половины плюс верхние/нижние 72% |
| Кружки | Три трети и пять перекрывающихся половин развёртки |
| Набор 6 значков | Шесть областей сетки 2×3 с перекрытием |
| Акриловые брелоки | Основная верхняя область и нижние элементы |
| Набор брелоков 2+1 | Нижние левая/правая области без упаковочного заголовка |
| Стикерпаки | Половины по двум осям для составных листов |

Точные нормированные координаты и revision=2 находятся в коде preset(label).
Целый исходник всегда остаётся первым представлением; всего не более 9.
Обрезка не дорисовывает обратную сторону. Неизвестный вид не получает
произвольный профиль. Индивидуальные asset overrides имеют приоритет.

Применение: выбранные профили сохраняются администратором через существующий
Manager.configure с текущей revision и аудитом system.visual-search. Не менять
настройку прямым SQL. При изменении ассортимента штатное фоновое задание берёт
актуальный каталог и эти же сохранённые профили. Хеш признаков включает исходные
пиксели, профиль, представление, версию алгоритма и модель. Новый товар получает
те же представления; изменённый файл/профиль пересчитывается, неизменённые
признаки берутся из кеша. Инференс пакетами до 8 ограничивает память при
массовом пополнении. Проверенное поколение активируется атомарно, предыдущее
сохраняется для отката. Отдельной ручной нарезки новых товаров не требуется.

Если вид содержит нестандартный макет, администратор задаёт override конкретного
исходного файла существующим редактором. Новая геометрия профиля увеличивает
revision и сначала проходит контроль на других кодах. Новые partial-профили
не создают зелёный статус до отдельной калибровки; похожесть не вероятность.

Дополнительная стадия поиска: dense SIFT768 по исходному кадру, затем выделенный
объект и при необходимости обработанный объект. Не более трёх дополнительных
запросов к тому же индексу; сильное взаимное совпадение деталей позволяет
закончить до дорогой обработки бликов. В rescue необходимы взаимные однозначные
соответствия, согласованная гомография и достаточная площадь совпадений в обоих
изображениях. Повторение одного элемента не увеличивает уверенность. Обычный
исходный поиск сохраняется, ветви не суммируют баллы и не создают новый green.

Размеры различаются по назначению: DINOv2-small224 — общий образ каждого
представления; SIFT — детали декодированного кадра до 960×960; U2NetP320 — маска;
DHAN256 — только ограниченная низкочастотная поправка, растянутая обратно на
исходные детали. Увеличение DHAN не заменяет детали поиска. Увеличение DINO
потребует новой версии признаков, полного пересчёта и отдельного сравнения.

Клиент принимает выбранный локальный файл до 16MiB/12Mpx, уменьшает его до 1600,
затем отправляет только видимый квадрат 960×960 JPEG90 и не более 2MiB. Серверный
лимит и правила явной передачи не расширены. При испытании реальные фото
уменьшаются до близкого размера; вручную размеченный ROI — приближение действий
оператора, не измерение реального жеста на смартфоне.

Реальные 28 фото/25 кодов заранее разделены по кодам на настройку 17 фото/15
товаров и независимую проверку 11 фото/10 товаров. Никакого обучения модели;
исходные фотографии не изменяются и не индексируются. Результаты и ограничения
фиксируются в отчёте установленного релиза. Следующие проблемные фотографии
пополняют отдельный регрессионный корпус; для следующего изменения нужна также
новая независимая группа. Не подменять качество выдачи запоминанием фото.

В0.3.1 hard deadline дополнительной стадии16s. Она начинается только если исходный запрос занял <=4s и нет другого ожидающего сотрудника: полный путь укладывается в существующие gateway22s/browser23s/nginx24s. После длинной очереди возвращается исходная выдача с budget_original_used; произвольное продление внешних таймаутов не требуется.

Ranking best-view-2.1: взаимная проверка теперь обязательна и для original confirmed/геометрического якоря. Сам порядок обычных cosine score не меняется; неподтверждённая повторяющаяся деталь не блокирует корректный rescue. Предел shortlist обычной ветви48, rescue128; метаданные отражают фактический предел.

Оговорка корпуса владельца: все фотографии доступны для визуального анализа физических особенностей. Отложенные10 кодов не используются для количественной настройки порогов, но это не слепое промышленное испытание. Первую действительно новую полевую группу сотрудники снимут после релиза.

## 0.3.2 — повтор при незавершённой дополнительной обработке

GUI отличает настоящий пустой результат завершённого поиска от пустого исходного
результата, когда optional стадия была занята, превысила бюджет, не выполнилась
или встретила смену поколения. Во втором случае сохраняются кадр и возможность
повторить поиск; сообщение не утверждает окончательное «Не найдено». Непустая
исходная выдача и выключенный Авто сохраняют прежнее поведение. Четыре статуса
проверены браузерной регрессией, настоящий processed/empty по-прежнему показывает
«Не найдено». DOM содержит только несекретные статус/количество/версию индекса
для приёмки; кадров, сессий и токенов в диагностике нет. Вычислительный алгоритм,
модели и профили0.3.1 остаются без изменений.
